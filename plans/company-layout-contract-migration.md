## 1. 为什么要迁移

当前通用链路的问题是：

- 同一页多张表时，通用边界可能混表。
- 跨页表的完整性被页级校验提前截断。例如大地经营表在第 20、23 页，
  第 20 页不可能出现第 23 页的“其他渠道签单保费”。
- 通用逻辑会为未识别列补默认期间，导致上季度数丢失。
- 普通空白曾被统一写 0，列错位后会把缺失伪装成真实 0。
- 相似标签会撞码，例如 LCR2/LCR3 的必测情景和自测压力情景。
- 公司 extractor 目前大多只能修补通用结果，无法在通用结果失败时接管。

迁移后的原则：

1. 已验证公司优先使用公司专属页码。
2. 已验证公司从整份 PDF 直接重建全部目标表。
3. 公司专属结果必须通过版式契约。
4. 契约失败时整表失败，不能让错列数据继续进入 STEP3。
5. 未迁移公司暂时保留通用链路，但不得静默产生假 0。

## 2. 当前实现

### 2.1 调用链

```text
PDF
  → 公司 YAML 路由
  → 公司专属 locate_company_tables()
  → 公司专属 extract_company_tables()
  → 公司 layout_contracts 校验
  → STEP3 标准化
  → STEP4 勾稽
```

公司专属 extractor 成功时，不再执行：

- 通用页内区域搜索
- 通用整页表格搜索
- 通用表格边界裁剪
- 通用页级完整性校验

### 2.2 已提供的公司接口

公司模块要实现以下可选函数：

```python
def locate_company_tables(
    pdf_bytes: bytes,
    table_configs: Sequence[Mapping[str, Any]],
) -> dict[str, list[int]]:
    """返回 {table_id: [物理页码]}。"""


def extract_company_tables(
    pdf_bytes: bytes,
    table_configs: Sequence[Mapping[str, Any]],
) -> dict[str, Any]:
    """返回 tables、logs、pages_by_table。"""
```

接口发现：

```python
locator, extractor = get_company_document_hooks(extractor_name)
```

实现位置：

- `services/company_extractors/__init__.py`
- `services/batch_processor.py`
- `services/batch_workflow.py`

### 2.3 规则和缓存失效

`rule_signature()` 会计算以下内容的指纹：

- 公司 YAML
- extractor Python 文件
- rule version
- extractor 名称

YAML 或 extractor 代码变化后，同一 PDF 的旧定位、旧中间表、旧标准结果会自动失效。
避免页面仍显示修改前的失败结果。

## 4. 公司级版式契约

每家公司必须在 YAML 中声明目标表的固定结构：

```yaml
company:
  canonical: 公司名
  extractor: company_extractor
  layout_contracts:
    SOLVENCY_MAIN:
      headers: [项目, 本季度数, 上季度数, 基本情景下季度预测数]
      min_rows: 15
      required_rows:
        - 认可资产
        - 认可负债
        - 实际资本
        - 最低资本
        - 核心偿付能力充足率
        - 综合偿付能力充足率
```

字段规则：

- `headers`：必须从第 1 列开始完全匹配。
- `min_rows`：含表头的最低行数。
- `required_rows`：必须在表体中找到的业务行。
- 契约失败时，表只保留表头，并记录失败原因。

页码规则：

- 公司 locator 可用后，优先通过表标题和公司正文结构定位。
- YAML `expected_pages` 用于结果校验和漂移提示，不再作为唯一依据。
- 已迁移公司不使用 `prefer` 回退到其他页面。

## 5. 零值、占位符与缺失

每家公司必须在 extractor 中明确判断：

| 源表表现 | 处理 |
| --- | --- |
| 明确写 `0` | 写数值 0 |
| 资本类金额行写 `-` / `--` | 仅在公司声明为零值的行写 0 |
| 核心指标写 `-` | 保持缺失并记录原因 |
| 空白 | 默认缺失，除非公司规则明确说明空白代表 0 |
| 预测期空白 | 默认缺失，不自动写 0 |
| 自测压力情景与必测同名 | 公司 extractor 明确排除其中一个 |

禁止：

- 在共享 normalizer 中全局把所有空白写成 0。
- 因为标签相似就把自测 LCR 覆盖到必测 LCR。
- 用通用数值量级规则猜测哪个值更合理。

## 6. 单家公司迁移 SOP

### 第 1 步：建立基线

每家公司复制 `plans/company-migration-template.md` 作为迁移记录。

保存以下结果到 `tmp/company_migration/<公司>/`：

- 各年份 PDF 页数
- STEP1 原始 matches
- 每张目标表的页码和表头
- 原始 rows 和 table_blocks
- STEP3 标准数据
- 缺失指标清单
- 关键指标核对值

至少覆盖 2022、2024、2025；有异常年份必须加入。

### 第 2 步：确认源表结构

逐表记录：

- 表标题
- 物理页码
- 是否跨页
- 列数
- 每列期间名称
- 主行、子行、分组行
- 合并单元格和换行标签
- 哪些 `-` 是 0，哪些是缺失

### 第 3 步：填写 YAML 契约

- 为六张目标表声明 `layout_contracts`
- 设置必要业务行和最少行数
- 配置公司 aliases、profile 和 extractor
- 对特殊主体写明“不适用”口径

### 第 4 步：实现公司页码定位

新增：

```python
def locate_company_tables(pdf_bytes, table_configs=()):
    ...
```

要求：

- 用公司表标题或正文结构定位，不依赖通用语义打分。
- 跨页表返回全部物理页。
- 原文确实没有的表返回空页码，并记录原因。

### 第 5 步：实现整份 PDF 表格提取

新增：

```python
def extract_company_tables(pdf_bytes, table_configs):
    ...
```

要求：

- 整份 PDF 只打开一次。
- 每张表按公司自己的行次/标题/列顺序解析。
- 跨页表在公司逻辑内合并。
- `rows` 和 `table_blocks` 同步。
- 表块页码必须准确，不能把第 21 页的 LCR 标成第 22 页。
- 结果幂等。

### 第 6 步：实现公司专属后处理

如果仍需要通用抽取作为后备：

- 后处理只能修补公司已知版式。
- 优先迁移为完整 `extract_company_tables()`。
- 不允许用共享匹配分数决定最终值。

### 第 7 步：编写黄金样本测试

至少覆盖：

- 表头完整匹配
- 本季度/上季度/累计/预测的数量
- 关键指标精确值
- 跨页行
- 占位符与真实 0
- 同名不同情景
- 契约故意缺失一列时必须失败
- 连续执行两次结果一致

### 第 8 步：跑端到端

```text
STEP1 定位
→ STEP2 公司专属提取
→ STEP3 标准化
→ STEP4 勾稽
→ STEP7 取数
```

确认日志出现“公司专属规则”，且没有执行通用页级抽表。

### 第 9 步：跨年回归

按实际可得年份逐年比较：

- 表数
- 列数
- 行数
- 标准编码集合
- 关键指标值
- 0 值数量
- 缺失原因
- 来源页码

### 第 10 步：更新文档并上线

- 更新 `plans/company-<公司>-extraction.md`
- 在本文登记迁移状态
- 更新 `agent.md` 的当前说明
- 提交前确认规则指纹会触发旧会话失效

优先选择：

- 有跨页经营表
- 有多个期间列
- 有 LCR 主行/子行
- 有大量换行标签
- 当前 extractor 已超过 300 行、维护明显困难

- 先自动生成候选契约。

- 目标表是否适用

不能因为特殊主体不用修复 extractor 就继续走通用猜测。

## 8. 验收标准

每家公司必须全部满足：

- 公司专属定位和提取成功。
- 不调用通用页级抽表。
- 六张目标表按原文实际披露处理。
- 表头列数与数据列数一致。
- 期间列完整且顺序正确。
- 关键指标与 PDF 原文逐项一致。
- LCR 六个指标的本季度和上季度值正确。
- 自测压力情景不覆盖必测情景。
- `-`、`--`、空白、真实 0 有明确区分。
- 契约失败时整表失败。
- 连续执行两次结果一致。
- 2022–2025 可得年份通过。
- 规则或代码变化后旧缓存自动失效。

## 9. 暂不继续使用通用流程的条件

迁移后的公司出现以下任一情况时必须停下修复：

- 公司 locator 未找到原文确实存在的表
- 契约表头不匹配
- 行数低于最低要求
- 期间列数量不符
- 关键指标缺失但 PDF 有值
- 来源页码错误
- 出现假 0

不能用“回退通用规则并凑出值”解决。

### 用户指定的重点指标

- `CONTRACT_LOSS_ABSORPTION_EFFECT`（特定类别保险合同损失吸收效应）：逐公司逐年核对最低资本主表，区分特定类别/特定类/特定类别合同等名称变体和损失吸收调整明细，核对本期、上期、金额单位；只在有明确披露语义时将占位符视为0，未披露不能补0。
- `PREMIUM_GROWTH`（规模保费同比增速）：逐公司逐年核对流动性监测表的本期/上期及百分比单位，禁止映射到签单保费，也不能用签单保费增速替代披露值。

### 空白=0与漏提数字的区分

- 用户确认：文件中存在指标行且原文数值为空白时，按0处理，适用于全部已映射数值指标。指标行不存在时保留缺失。
- 标准化阶段不再仅凭提取结果为空就填0。公司文档提取入口保存原PDF线框单元格坐标，并独立检查该坐标内的PDF文字；存在文字、缺少坐标或合并单元格不清楚时，不出具空白确认。
- 证据按物理页码、标准化行标签、期间列位置绑定；只有对应证据存在才输出0，并在备注中记录“原PDF单元格已确认空白，按用户口径0处理”。未确认的提取空白写入待核对诊断，不能混入0。
- 已在九家公司共享文档入口接入坐标检查。其他专属/通用入口尚未提供证据的空白保留待核对；不能据此宣称所有公司的空白已自动核实。大地原有明确短横线/0规则继续生效。
